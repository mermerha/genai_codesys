# 面向 CODESYS 的 ST 代码生成 Agent：报告大纲

> 本文件用于指导正式报告写作。报告以课程作业要求为主线，围绕数据集与 Spec、自研框架、实验设计、结果与分析展开。项目改进过程放在自研框架章节中，用来解释最终设计是怎样形成的。

## 1. 报告的核心叙事

PLC 程序的正确性包含两个层面：代码能够通过编译，以及控制行为满足需求。大模型可以生成 ST 代码，但模型输出需要经过真实的 CODESYS 编译和功能测试，才能判断是否完成任务。

因此，报告按照下面的思路推进：

```text
先说明 PLC 代码生成面临什么问题
→ 用题目、LTL Spec 和测试定义什么叫正确
→ 根据这些要求设计生成、编译和修复框架
→ 在开发中发现问题并逐步形成最终方案
→ 固定环境和公平条件开展四组实验
→ 用编译、测试和案例分析回答系统表现如何
```

报告需要形成三个主要结论：

1. 模型已经能够生成大量可编译 ST 代码，但编译成功和功能正确之间仍有明显差距。
2. 自研 harness 的主要作用是组织上下文、约束候选格式、调用 CODESYS、反馈错误、控制终止并保存证据。
3. 最终正式实验共运行 120 个条件，96 个条件通过编译，53 个条件通过本题全部测试。

### 2.4 LTL Spec 编写

以老师示例中的电机启停题为主例，按以下过程展开：

```text
自然语言需求
→ 识别输入、输出和状态
→ 定义命题
→ 区分安全、响应、保持和优先级要求
→ 写成 LTL
→ 与接口和测试相互检查
```

正文只解释项目实际使用的基本语义：

- `G` 表示性质始终成立。
- `X` 表示本次输入经过一次 PLC 扫描后的状态。
- 安全性质描述必须避免的行为。
- 响应和保持性质描述系统应怎样变化。

全部 30 道题的 136 条性质放入附录 B，正文展示电机启停题和一项多阶段任务即可。

### 2.5 测试用例设计

测试用例参考老师提供的 Word 模板，每个用例包括名称、所属题目、初始状态、输入步骤、预期输出、覆盖内容、实际输出和结果。

因为 PLC 行为随扫描周期推进，测试按多个步骤组织：

```text
设置初始状态
→ 写入本周期输入
→ 等待扫描稳定
→ 读取公开输出
→ 与预期值比较
→ 进入下一步骤
```

测试设计遵循以下规则：

- 覆盖正常流程、状态变化、冲突输入、安全优先级和边界条件。
- 只使用公开输入建立状态，不修改候选内部变量。
- 同一道题在四种设置下使用同一份测试和判断标准。
- 编译失败时，该题计划测试均计为未通过。

## 第 3 章 自研 Agent harness：从最小闭环到最终方案

在正确性标准明确后，本章说明系统怎样生成代码、调用工具和处理反馈。改进过程融入设计原因，避免单独罗列代码版本。

### 3.1 最初的实现思路

项目开始时先建立最小闭环：读取一道题，调用模型生成 ST，写入模板工程，调用 CODESYS 编译；若编译失败，就把错误反馈给模型，最多修复两次。

这样做先验证了最关键的外部边界，也暴露出后续问题：部分候选接口明显错误仍会启动 CODESYS；题目语义只靠自然语言表达；编译和测试各启动一次 CODESYS，运行开销较大。

### 3.2 根据问题形成的改进

改进按照实际问题依次进行：

1. 因为接口错误可以在本地确定，所以加入候选预检，检查 POU 名称、类型、声明头和公开接口。
2. 因为编译通过后仍存在较多功能错误，所以将逐题 LTL Spec 加入两个框架的共享任务上下文，帮助模型明确安全、保持和状态变化要求。
3. 因为测试脚本本身会重新编译工程，所以将编译与测试合并为一次 CODESYS 执行，减少重复启动。
4. 因为测试结果属于最终评价依据，所以测试始终不反馈给模型，避免泄露答案和破坏公平性。

报告中可以用一张问题—修改—结果表概括改进，不使用代码版本编号。

### 3.3 最终总体架构

```text
冻结题目与 Spec
→ 提示词构建
→ 模型生成结构化候选
→ 候选解析与接口预检
→ CODESYS 编译
→ 编译失败：反馈错误并修复
→ 编译成功：执行共享测试
→ 保存证据与最终状态
```

### 3.4 任务组织与上下文管理

- 每次只处理一道冻结题目。
- 初次生成提供需求、接口、编译上下文和 LTL Spec。
- 修复时只增加上一候选和编译错误。
- 不输入其他题目、项目历史和测试答案。

这样可以控制上下文长度，也使每一次模型调用的依据清楚。

### 3.5 候选格式和工具调用

模型输出 `pou_name`、`pou_type`、`declaration` 和 `implementation` 四个字段。结构化格式便于严格解析，并可以直接写入 CODESYS 工程。

工具调用只保留两类必要操作：模型生成候选，以及 CODESYS 编译测试。确定无效的候选在预检阶段结束，不启动外部工具。

### 3.6 编译、错误反馈与修复

候选功能块会在临时 `PLC_PRG` 中实例化并调用，保证其代码真正进入编译链。编译失败时，系统提取错误对象、位置和文本，下一轮模型根据上一候选和错误信息修复。

每题最多有三个候选。达到上限后停止，避免重复调用和无限循环。

### 3.7 自动功能测试

编译通过后，系统在 CODESYS Simulation 中完成：

```text
复位应用
→ 写入公开输入
→ 等待 PLC 扫描
→ 读取公开输出
→ 对比预期输出
→ 保存失败步骤和差异
```

自动测试是本项目实际完成的进阶内容，也为编译通过与功能正确的区别提供了直接证据。

### 3.8 课堂内容与设计联系

这里保留课程课件的第二处内容：`pptcourse/1102.pdf` 中 propose—check—repair 流程。

项目中的对应关系为：模型提出候选，候选预检和 CODESYS 负责检查，编译错误驱动下一轮修复。测试作为独立评价门，在候选生成结束后判断功能结果。

### 3.9 现成 Agent 基线

Codex CLI 使用相同模型、题目、Spec、候选次数和 CODESYS 执行器。它负责生成结构化候选，外部 Python 循环将编译错误传递给下一轮。这样能够在共享工具和测试标准下比较现成 Agent 与自研 harness。

## 第 6 章 结果分析与代表案例

### 6.1 为什么编译通过后仍会失败

最终实验中有 96 个条件通过编译，其中只有 53 个条件通过本题全部测试。剩余 43 个条件说明代码的语法和接口已经被 CODESYS 接受，但状态保持、优先级、定时或阶段推进仍有错误。

这里回扣第 1 章的问题：编译器检查语言和工程结构，功能测试检查需求对应的行为。二者共同使用，才能得到更可信的结论。

### 6.2 模型差异

DeepSeek 的最终编译率为 100%，Qwen 为 60%；两者测试通过率分别为 73.37% 和 38.04%。从代表性失败看，Qwen 更容易在接口、状态推进和复杂控制语义上出错。因此，在本实验范围内，模型能力是影响结果的主要因素之一。

### 6.3 框架差异

Codex CLI 的任务成功率为 46.67%，自研 harness 为 41.67%。两种框架的差距小于两个模型之间的差距，而且不同模型下的框架差异并不一致。

因此，报告不把自研框架是否超过现成框架作为唯一判断。自研 harness 的主要成果是建立了清晰、可控、可复现的 PLC 代码生成实验链路，这也符合课程对框架逻辑、公平性和证据的要求。

### 6.4 题目难度与表达方式

简单题通常包含直接控制和单一锁存；复杂题加入多模式、多阶段、数组、定时和复位条件。自建题经过统一接口和人工审核，需求边界更清楚，因此整体成功率高于公共题。

这一结果说明，除了模型和框架，题面是否清晰、Spec 是否完整也会影响生成质量。

### 6.5 成功案例：`public_20`

`public_20` 是五工位生产控制任务，属于 hard。四种设置均编译成功并通过 4/4 测试。

案例按以下顺序展开：

```text
任务要求
→ 关键状态和 Spec
→ 候选控制结构
→ 测试步骤
→ 四组结果
→ 成功原因
```

### 6.6 语义失败案例：`custom_06`

四种设置全部通过编译，但没有一组通过全部测试。该题涉及填充、混合和排空三个阶段，以及定时和状态推进。

重点展示一个失败步骤，说明候选在哪个状态转换上与预期不一致。这个案例直接支撑编译通过不能代表任务完成。

### 6.7 模型与框架差异案例：`public_19`

该题包含手动、单步、单周期和连续模式。四组均通过编译，只有 Codex CLI + DeepSeek 通过全部 4 个测试。

对比模式互斥、状态推进和复位逻辑，说明模型与框架组合会影响复杂流程任务的实现结果。

### 6.8 失败类型

代表性失败可以归纳为：

- 候选格式和公开接口错误。
- 数据类型和数组绑定错误。
- 状态保持遗漏。
- 停止、急停和故障优先级错误。
- 多阶段流程跳转错误。
- 定时和复位边界错误。

如果没有对全部失败候选完成人工编码，正文只使用案例表，不绘制失败类型比例图。

### 6.9 局限

- 实验固定在一台电脑和一个 CODESYS 版本。
- 每个条件只正式运行一次，模型输出存在随机性。
- 初始实现到最终实现同时改进了多个部分，因此该对比属于完整系统迭代，不能作为单变量消融实验。
- LTL 已用于需求组织和模型上下文，但没有接入 PLCVerif。
- 92 个测试覆盖主要行为，不能穷尽全部输入和状态。
- Codex CLI 缺少可直接使用的费用数据，因此不推算其成本。

## 第 7 章 结论

结论按项目完成情况、实验发现和项目价值依次收束。

首先总结完成内容：30 道题、136 条 LTL、92 个测试用例、自研 harness、Codex CLI 基线、自动编译测试和 120 次正式运行。

随后总结实验发现：DeepSeek 整体优于 Qwen；两个框架都能完成部分 PLC 任务；编译率明显高于任务成功率，功能语义仍是主要难点。

最后说明项目价值：建立了从自然语言需求到 ST 候选、CODESYS 编译、功能测试和证据分析的完整流程，并通过问题驱动的改进形成最终方案。

展望只保留与现有项目直接相关的三点：

- 将 LTL 接入 PLCVerif，形成真正的形式化验证步骤。
- 对同一条件进行多次重复实验，分析模型输出波动。
- 研究在不泄露测试答案的前提下利用功能反馈修复代码。
