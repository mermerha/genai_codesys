# PLC ST 代码生成大作业报告计划

## 1. 写作目标

本报告围绕一个问题逐步展开：如何让大模型生成的 ST 代码进入真实的 CODESYS 编译和测试环境，并用公平、可复现的实验评价生成质量。

正文按照以下思路推进：

```text
项目目标
→ 数据集与正确性标准
→ 自研 Agent 如何工作
→ 如何进行公平实验
→ 实验得到什么结果
→ 为什么出现这些结果
→ 项目结论与局限
```

作业原始要求见 [`genai/Final project_CHINESE.pdf`](genai/Final%20project_CHINESE.pdf)。

## 2. 写作风格

- 表达清晰、简明，先讲问题，再讲方法和结果。
- 使用口语化但正式的中文，避免堆砌术语。
- 少用防御性句式，不反复解释项目没有做什么。
- 不使用带双引号的比喻。
- 可以少量使用“我们”，用于引导读者理解设计过程。
- 结果章节先陈述数据，分析章节再讨论原因。
- 推测性内容使用“可能”“从结果看”等表述，不写成确定事实。
- 所有报告数字必须能够追溯到正式实验原始记录和汇总文件。

## 3. 推荐正文结构

### 摘要

回答四个问题：

1. 项目解决什么问题。
2. 实现了什么系统。
3. 怎样完成四种设置的公平实验。
4. 得到了什么主要结论。

摘要中给出关键规模与结果：

- 20 道公共题和 10 道自建题。
- 30 份逐题 LTL Spec、92 个测试用例。
- 自研 harness 与 Codex CLI 两个框架。
- DeepSeek 与 Qwen 两个模型。
- 120 次正式实验。
- 自研 harness + DeepSeek 的任务成功率最高，为 60.00%。

建议篇幅：半页以内。

## 第 1 章 引言

### 1.1 项目背景

- ST 是 PLC 常用编程语言。
- PLC 程序涉及设备接口、控制顺序、状态保持和安全逻辑。
- 大模型可以生成 ST 代码，但生成结果仍需经过真实编译和功能测试。
- 本项目构建生成、编译、修复、测试和证据保存的完整流程。

### 1.2 项目目标

介绍项目完成的主要内容：

- 公共题与自建题数据集。
- 逐题 LTL 规约与共享测试用例。
- 轻量级自研 Agent harness。
- Codex CLI 基线。
- CODESYS 自动编译与自动功能测试。
- 两个框架、两个模型的四种设置实验。

### 1.3 项目范围

- LTL 用于表达题目预期性质。
- 已实现自动功能测试。
- 未接入 PLCVerif，因此不报告形式化验证通过率。
- 不扩展 TIA Portal 和多 Agent 等非必要功能。

## 第 4 章 自研 Agent harness 设计

### 4.1 设计目标

- 数据流清楚。
- 编译反馈能够直接用于修复。
- 实验过程可保存、可复现、可比较。
- 保持轻量，避免不必要的多层抽象。

### 4.2 总体架构

```text
任务与配置
→ 提示词与模型调用
→ 候选解析与接口检查
→ CODESYS 编译
→ 编译反馈与修复
→ 共享功能测试
→ 原始证据与结果汇总
```

### 4.3 任务组织

- 每次处理一道冻结题目。
- 读取需求、接口和必要编译上下文。
- 按生成、编译、修复、测试顺序执行。

### 4.4 上下文管理

- 只向模型提供当前题目和必要接口。
- 修复时增加上一候选和编译错误。
- 不向模型提供测试用例。
- 避免重复输入整个项目和无关历史。

### 4.5 候选格式与工具调用

模型输出严格包含：

- `pou_name`
- `pou_type`
- `declaration`
- `implementation`

说明该格式如何减少解析歧义并方便写入 CODESYS。

### 4.6 编译与修复

```text
生成候选
→ 严格解析
→ 写入临时工程
→ CODESYS 编译
→ 编译失败：反馈结构化错误并修复
→ 编译成功：进入共享功能测试
```

重点说明：

- 功能块在临时 `PLC_PRG` 中实例化和调用。
- 避免未引用功能块产生假编译成功。
- 最多允许两个修复轮次。

### 4.7 自动功能测试

- 冷复位应用。
- 写入公开输入。
- 等待 PLC 扫描。
- 读取公开输出。
- 与预期输出比较。
- 保存失败步骤与差异。

### 4.8 终止条件与证据保存

终止状态包括：

- 编译且全部测试通过。
- 编译通过但测试失败。
- 达到最大候选次数。
- 模型或外部工具超时。
- 明确基础设施故障。

保存题目、配置、模型响应、候选代码、编译结果、测试结果和最终状态。

### 4.9 Codex CLI 基线

- 使用 `codex exec` 生成结构化候选。
- 与自研 harness 共用 CODESYS 编译和测试执行器。
- 编译反馈由外部循环传递。
- 不向基线 Agent 提供测试用例。

## 第 7 章 结果分析与案例

### 7.1 模型差异

- DeepSeek 的编译率和功能正确率明显高于 Qwen。
- Qwen 在复杂题中更容易出现语法、状态推进和接口理解问题。
- 从当前结果看，模型能力是主要影响因素。

### 7.2 框架差异

- 相同 DeepSeek 模型下，自研 harness 的任务成功率和测试通过率略高。
- 两个框架的首次编译率接近。
- 自研 harness 的上下文更短，Token 消耗明显低于 Codex CLI。
- 框架带来一定差异，但不夸大为决定性优势。

### 7.3 难度影响

- easy 题主要考察接口遵循和直接控制逻辑。
- medium、hard 题包含状态机、时序、数组和多阶段流程。
- 编译成功后仍可能存在功能错误。
- 测试结果比单独的编译结果更能反映功能质量。

### 7.4 公共题与自建题差异

- 四种设置在自建题上的成功率均高于公共题。
- 可能与自建题经过接口整理、任务边界更清楚有关。
- 公共题中部分需求更长，状态和接口更复杂。

### 7.5 成功案例

建议选择 `public_06`：四种设置均成功。

统一展示：

```text
题目要求
→ 关键 Spec

→ 编译结果
→ 测试结果
→ 成功原因
```

### 7.6 差异案例

建议选择：

- `public_13`：DeepSeek 成功，Qwen 只通过部分测试。
- `public_19`：复杂流程任务，不同模型和框架出现明显差异。

### 7.7 失败类型

按以下类别整理代表案例：

- ST 语法或候选格式错误。
- 接口和数据类型错误。
- 状态保持错误。
- 控制优先级错误。
- 多阶段流程推进错误。
- 定时和边界条件错误。

可以使用分类表。若后续对全部失败结果进行人工编码，再补充失败类型分布图。

### 7.8 有效性与局限

- 实验固定在一台电脑和一个 CODESYS 版本。
- 每题每种设置只正式运行一次，存在模型随机性影响。
- Codex CLI 没有可直接使用的费用数据。
- LTL 已编写，但没有接入 PLCVerif。
- 测试覆盖主要行为，不能证明所有可能输入均满足要求。
- 数据集总量为 30 道题，结论适用于本次课程项目范围。

## 第 8 章 结论

按三层总结：

1. 完成内容：数据集、LTL、自研 harness、Codex CLI 基线、自动编译、自动测试和 120 次实验。
2. 实验结论：DeepSeek 整体表现更好；自研 harness 在部分指标和资源消耗上具有优势；编译通过不能代表功能正确。
3. 项目价值：建立了从自然语言需求到 ST 代码、CODESYS 编译、自动测试和证据汇总的完整流程。
