# 项目执行流程

本文件描述从当前状态到最终提交的完整流程。阶段 1 的接口设计与阶段 2 的只读环境盘点、最小可行性验证可以并行；但阶段 3 的正式 harness 实现必须等待两者的关键出口条件满足。其他阶段原则上按顺序推进。

## 阶段 0：建立项目治理

工作：建立目录、长期规则、要求清单、状态、决定和数据接口。

出口条件：

- 项目入口和目录职责明确。
- 已完成、未完成和下一步能够从状态文件读取。
- 老师原始材料保持不变。

当前状态：已完成初版。

## 阶段 1：冻结最小接口与实验规则

工作：

- 确定团队成员和责任人。
- 确定公共题、自建题、LTL、测试和实验结果的字段。
- 确定同题同测试、正式实验冻结、失败记录等公平规则。
- 确定模型 A、模型 B 和现成 Agent 候选。

出口条件：

- `docs/DATA_CONTRACT.md` 从草案变为已确认。
- 关键选择写入 `docs/DECISIONS.md`。
- 一道标准样题能够完整表示题目、规约和测试。

标准联调样例固定为 `tests/fixtures/motor_start_stop_fixture.json`。它来自老师示例，仅用于接口和环境测试，不计入 20 道公共题或 10 道自建题。

## 阶段 2：环境可行性验证

工作：

- 记录 Windows、Python、CODESYS、Profile、编译器、设备和库版本。
- 确认 CODESYS Scripting 可用。
- 创建固定模板工程。
- 自动编译一份已知正确 ST 和一份已知错误 ST。
- 验证能提取错误文本、严重级别和位置。
- 验证 DMXAPI 的一个模型调用，但不在文件中保存真实 Key。

出口条件：

- 正确代码返回编译成功。
- 错误代码返回结构化失败结果。
- 命令、配置和日志已保存。
- 环境能够由 README 说明复现。

## 阶段 3：单题 Agent 最小闭环

工作：

- 读取一道标准题。
- 调用一个模型生成结构化 ST。
- 将声明和实现写入模板工程。
- 编译、提取错误、修复并再次编译。
- 设置最大轮次、超时和终止原因。
- 保存每轮提示词、响应、候选代码和编译结果。

出口条件：

- 一道简单题无需手工复制即可完成生成到编译。
- 至少验证一次真实编译错误反馈修复。
- 连续失败能够正常终止，不会无限循环。

## 阶段 4：构建并审核完整数据集

工作：

- 转换 20 道公共题。
- 生成、筛选并审核不少于 10 道自建题。
- 生成 LTL 和测试初稿。
- 人工审核题目、规约和测试的一致性。
- 检查 JSON、ID、变量名和引用。

出口条件：

- 至少 30 道题全部通过数据校验。
- 每题都有来源/合成记录、LTL 和测试。
- 测试覆盖要求已人工签核。

## 阶段 5：接入完整实验矩阵

工作：

- 接入模型 A、模型 B。
- 接入现成 Agent 基线。
- 建立四种设置的统一配置。
- 建立批量运行、断点续跑和不可覆盖的结果目录。
- 先用 3 至 5 道、不同难度题目预跑。

出口条件：

- 四种设置都能运行同一道题。
- 同题使用相同测试和判定标准。
- 预跑结果可从原始记录重建汇总表。

## 阶段 6：冻结并执行正式实验

工作：

- 冻结代码版本、提示词、模型参数、CODESYS 环境、数据和测试。
- 记录冻结版本标识。
- 在统一正式实验环境完成至少 120 次任务运行。
- 记录异常、超时、重试和任何环境问题。

出口条件：

- 四种设置全部覆盖完整题库。
- 没有无解释的缺失结果。
- 所有汇总数字能够追溯到原始文件。

## 阶段 7：分析、报告和汇报

工作：

- 计算编译、测试、修复、时间和资源指标。
- 分析模型、框架和难度差异。
- 选取代表性成功和失败案例。
- 完成架构图、流程图、报告、PPT、演示录屏和答辩材料。
- 在干净环境检查 README 和提交包。

出口条件：

- 报告数字与汇总文件一致。
- PPT 与报告结论一致。
- 最终提交清单全部勾选。
- 基础任务完整，未完成的加分项明确标注而非伪装完成。
